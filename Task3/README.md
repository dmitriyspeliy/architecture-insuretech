# Задание 3. Переход на Event-Driven архитектуру

## 1. Текущая схема взаимодействия

Сейчас `core-app` и `ins-comp-settlement` получают данные о продуктах и тарифах через синхронный REST-вызов в `ins-product-aggregator`.

`ins-product-aggregator` в рамках одного запроса обращается к API всех страховых компаний, агрегирует ответы и возвращает единый список. `core-app` делает такой запрос раз в 15 минут, а `ins-comp-settlement` — раз в сутки при формировании реестра взаиморасчётов.

Дополнительно `ins-comp-settlement` раз в сутки вызывает `core-app` по REST API, чтобы получить все оформленные за день страховки.

## 2. Проблемы и риски текущей архитектуры

| Проблема / риск | В чём проблема | Последствие при росте с 5 до 10 страховых компаний |
| --- | --- | --- |
| Синхронная агрегация тарифов | `ins-product-aggregator` ждёт ответы от всех страховых компаний в рамках одного запроса | Увеличивается latency, чаще появляются timeout и частичные ошибки |
| Жёсткая связность сервисов | `core-app` и `ins-comp-settlement` зависят от доступности `ins-product-aggregator` и внешних API страховых компаний | Ошибка одной страховой компании может влиять на внутренние сервисы InsureTech |
| Дублирующие pull-запросы | Разные сервисы самостоятельно запрашивают одни и те же справочные данные | Лишняя нагрузка на `ins-product-aggregator` и внешние API |
| Неравномерная актуальность данных | `core-app` обновляет данные раз в 15 минут, `ins-comp-settlement` — раз в сутки | В разных сервисах могут использоваться разные версии тарифов |
| Суточный REST-запрос из `ins-comp-settlement` в `core-app` | Все оформленные страховки за день забираются одним большим batch-запросом | Рост объёма данных увеличит время выполнения, риск timeout и неполной выгрузки |
| Сложность повторной обработки | При ошибке синхронного вызова нужно повторять весь запрос целиком | Трудно обеспечить идемпотентность и точечную обработку только неуспешных записей |
| Нет естественной истории изменений | Сервисы получают текущее состояние, но не поток изменений | Сложнее расследовать расхождения, переигрывать данные и строить read-model |
| Риск каскадной деградации | Медленные внешние API страховых компаний замедляют внутренние запросы | При росте числа интеграций деградация одной компании может влиять на всю цепочку |

## 3. Предлагаемое решение

Не меняя функциональную декомпозицию сервисов, внутренние регулярные REST-pull взаимодействия нужно заменить на Event Streaming.

Добавляется брокер событий, например Kafka. Сервисы сохраняют свои зоны ответственности:

- `ins-product-aggregator` по-прежнему отвечает за интеграцию со страховыми компаниями и нормализацию продуктов/тарифов.
- `core-app` по-прежнему отвечает за оформление страховок и пользовательские сценарии.
- `ins-comp-settlement` по-прежнему отвечает за взаиморасчёты со страховыми компаниями.

Меняется только способ обмена данными между внутренними сервисами.

## 4. Какие взаимодействия переводятся на Event Streaming

| Было | Стало |
| --- | --- |
| `core-app` раз в 15 минут вызывает `ins-product-aggregator` по REST для получения продуктов и тарифов | `ins-product-aggregator` публикует события `ProductCatalogUpdated` / `ProductTariffUpdated`; `core-app` потребляет события и обновляет локальную read-model |
| `ins-comp-settlement` раз в сутки вызывает `ins-product-aggregator` по REST для получения продуктов и тарифов | `ins-comp-settlement` потребляет те же события продуктов и тарифов и поддерживает локальную read-model |
| `ins-comp-settlement` раз в сутки вызывает `core-app` по REST для получения оформленных страховок | `core-app` публикует события `InsurancePolicyIssued`, `InsurancePolicyPaid`, `InsurancePolicyCancelled`; `ins-comp-settlement` потребляет их и формирует свою базу для взаиморасчётов |

Внешние вызовы к API страховых компаний остаются синхронными REST/SOAP/GraphQL, потому что внешние системы не находятся под контролем InsureTech. Для них нужны timeout, retry с backoff, circuit breaker и изоляция интеграций по компаниям.

## 5. Предлагаемые топики

| Топик | Publisher | Consumer | Назначение |
| --- | --- | --- | --- |
| `product-catalog-events` | `ins-product-aggregator` | `core-app`, `ins-comp-settlement` | Изменения продуктового каталога |
| `product-tariff-events` | `ins-product-aggregator` | `core-app`, `ins-comp-settlement` | Изменения тарифов и условий страховых продуктов |
| `insurance-policy-events` | `core-app` | `ins-comp-settlement` | События оформленных, оплаченных, отменённых страховок |
| `*.dlq` | Broker / consumers | Support / retry processor | События, которые не удалось обработать после заданного числа попыток |

## 6. Transactional Outbox

Паттерн Transactional Outbox использовать нужно.

### Где использовать обязательно

1. В `core-app`.

   При оформлении страховки `core-app` должен в одной DB-транзакции:

    - сохранить заявку / страховку в `core-db`;
    - записать событие в outbox-таблицу, например `InsurancePolicyIssued`.

   Отдельный publisher-процесс читает outbox и публикует событие в Kafka.

2. В `ins-product-aggregator`, если сервис сохраняет нормализованный snapshot продуктов и тарифов в своей БД.

   В одной транзакции сервис должен:

    - обновить сохранённый snapshot продукта/тарифа;
    - записать событие `ProductCatalogUpdated` или `ProductTariffUpdated` в outbox.

### Зачем это нужно

Без Transactional Outbox возможна ситуация, когда данные в БД уже изменились, но событие в брокер не было отправлено из-за ошибки сети, падения процесса или недоступности Kafka. Тогда `ins-comp-settlement` не узнает об оформленной страховке, а `core-app` или `ins-comp-settlement` могут не получить актуальный тариф.

Transactional Outbox убирает это окно рассинхронизации между БД и брокером.

## 7. Идемпотентность и порядок обработки

Для событий нужны стабильные идентификаторы:

- `eventId` — уникальный ID события;
- `aggregateId` — ID продукта, тарифа или страховки;
- `eventType` — тип события;
- `occurredAt` — время возникновения события;
- `version` — версия агрегата или события.

Consumer должен быть идемпотентным. Для этого можно хранить таблицу обработанных событий, например `processed_events`, с уникальным индексом по `event_id`.

Для Kafka partition key лучше использовать:

- `productId` для продуктовых и тарифных событий;
- `policyId` для событий оформленных страховок.

Так сохраняется порядок событий внутри одного продукта или одной страховки.

## 8. Обработка ошибок

Рекомендуемый подход:

- retry с ограниченным числом попыток;
- backoff между попытками;
- dead-letter topic для событий, которые не обработались;
- мониторинг consumer lag;
- алерты на рост DLQ, lag и ошибки публикации из outbox;
- ручной или автоматизированный replay событий.

## 9. Итоговая целевая модель

Целевая архитектура снижает связность внутренних сервисов:

- `core-app` и `ins-comp-settlement` больше не зависят от синхронного ответа `ins-product-aggregator` при обновлении продуктов и тарифов;
- `ins-comp-settlement` больше не делает суточный bulk-запрос в `core-app` для оформленных страховок;
- каждый сервис поддерживает свою локальную read-model через поток событий;
- ошибки внешних страховых API изолируются внутри `ins-product-aggregator` и не блокируют внутренние сервисы напрямую;
- за счёт Transactional Outbox снижается риск потери событий при изменении данных в БД.
